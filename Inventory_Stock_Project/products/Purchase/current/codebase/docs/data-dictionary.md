## 1. `inventory_stock.silver_fact.fact_purchase`

**Purpose:** Grain-level purchase order line fact table. Each row represents one purchase order line, uniquely identified by the surrogate key `purchase_key`. Loaded via Spark SQL `MERGE INTO` from `bronze.purchase_staging` after SCD-2 surrogate key resolution. Clustered by `(date_key, supplier_key)` for optimal analytical query performance.

**Grain:** One row per purchase order line × supplier × stock item × order date.

**Load pattern:** `MERGE INTO` (upsert) from `bronze.purchase_staging` via `migrate_staged_purchase_data.py`. Match predicate: `(wwi_purchase_order_id, date_key, supplier_key, stock_item_key)`.

**Delta properties:** `autoOptimize.optimizeWrite = true`, `autoOptimize.autoCompact = true`. `CLUSTER BY (date_key, supplier_key)`. Fallback for pre-DBR 13.3: `PARTITIONED BY (date_key)` + post-DDL `OPTIMIZE … ZORDER BY (supplier_key, stock_item_key)`.

**Rules:** OB-002, TY-004, TY-010, TY-003, TY-009, TY-015, TY-017, PE-002, PE-008, PE-P001, LN-001, NM-001, NM-009, CX-P006

Auto-generated by Delta's `GENERATED ALWAYS AS IDENTITY` mechanism; no source equivalent. | Uniquely identifies a single purchase order line in the target data platform. Carries no business meaning; used as a stable row identifier for BI joins and incremental processing. | `BIGINT GENERATED ALWAYS AS IDENTITY` — assigned by Delta on `MERGE INSERT`; replaces no legacy column (the legacy fact table also had a surrogate PK, not explicitly migrated). ## 2. `inventory_stock.bronze.purchase_staging`

**Purpose:** Bronze landing table for raw purchase order line extracts from the source OLTP system. Loaded via full OVERWRITE per batch run, eliminating the stale-row accumulation defect from the legacy SSIS pipeline (which truncated the wrong table `Integration.Order_Staging`). Surrogate key columns (`supplier_key`, `stock_item_key`) are NULL at extract time and populated by `sk_resolver.py` before the fact MERGE.

**Grain:** One row per extracted purchase order line per ETL run.

**Load pattern:** Full OVERWRITE by `nb_extract_purchase`. Surrogate keys updated in-place by `sk_resolver.py` before `migrate_staged_purchase_data.py` reads the table.

**Delta properties:** `autoOptimize.optimizeWrite = false`, `autoOptimize.autoCompact = false` (ephemeral staging; auto-optimize overhead is not warranted).

**Rules:** OB-003, OB-P002, TY-017, TY-015, TY-010, TY-004, TY-003, TY-009, LN-001, NM-001, NM-002, CX-P006

| # | Column Name | Data Type | Nullable | Description | Business Meaning | Derivation / Source |

Auto-generated by Delta's `GENERATED ALWAYS AS IDENTITY` on insert. | Uniquely identifies a staging row for use as the partition key in `sk_resolver.py` window functions (`PARTITION BY purchase_staging_key`). ## 3. `inventory_stock.bronze.lineage_run`

Change Data Feed (CDF) is enabled to support downstream lineage tracking queries. Opened at the start of each pipeline run by `open_lineage_record()`; closed at the end by `close_lineage_record()`.

**Grain:** One row per ETL pipeline execution.

**Load pattern:** `INSERT` by `open_lineage_record()` at run start (Task 1); `UPDATE` by `close_lineage_record()` at run end (Task 3).

**Delta properties:** `delta.enableChangeDataFeed = true`, `delta.autoOptimize.optimizeWrite = true`.

**Rules:** LN-001, LN-002, OB-004, TY-017, NM-001, CX-P006

## 4. `inventory_stock.bronze.etl_cutoff`

**Purpose:** Watermark control table. Stores the high-watermark timestamp per tracked table, used by `nb_extract_purchase` to bound each incremental extract window. Replaces `integration.etl cutoff` from the legacy SQL Server system (space in name resolved per NM-002). One row per tracked table.

**Grain:** One row per tracked target table name.

**Load pattern:** Read by `get_last_etl_cutoff()` in Task 1; updated by `set_etl_cutoff()` in Task 3 after a successful MERGE.

**Delta properties:** Standard Delta managed table, no special properties.

**Rules:** LN-005, OB-004, NM-001, CX-P006

| # | Column Name | Data Type | Nullable | Description | Business Meaning | Derivation / Source |
|---|---|---|---|---|---|---|
| 1 | `table_name` | STRING | No | Name of the target table this watermark row tracks (e.g. `fact_purchase`). Acts as the logical primary key. | Scopes the watermark to a specific table, allowing multiple products to share a single `etl_cutoff` table with one row each. | Passed as a parameter to `get_last_etl_cutoff(spark, "fact_purchase")` and `set_etl_cutoff(spark, "fact_purchase", new_cutoff)`. Source: `integration.etl cutoff.TableName` (legacy); space resolved per NM-002. |
| 2 | `cutoff_time` | TIMESTAMP | No | The high-watermark timestamp marking the upper boundary of the last successful incremental extract. The next run extracts rows where `last_modified_when > cutoff_time`. | Controls the incremental extraction window, ensuring each run picks up only new or updated rows since the last successful run. Prevents re-extraction of already-processed data. | Updated by `set_etl_cutoff(spark, "fact_purchase", new_cutoff)` after a successful MERGE. Source: `integration.etl cutoff.Cutoff Time` (legacy, DATETIMEOFFSET → TIMESTAMP per TY-022). |
| 3 | `last_updated_utc` | TIMESTAMP | No | UTC timestamp of when this row was last updated by `set_etl_cutoff()`. | Audit column tracking when the watermark was last advanced; enables detection of stalled pipelines (watermark not updated as expected). | Set to `current_timestamp()` by `set_etl_cutoff()` on each successful update. New audit column — no direct legacy equivalent. Rule: NM-009. |

## 5. `inventory_stock.bronze.dq_rejections`

**Purpose:** Centralised DQ rejection store. Any record that fails a quality rule during the bronze-to-silver promotion step is written here with full context: violated rule ID, source table, primary key value, offending column, and rejection reason. Linked to the originating pipeline run via `lineage_key`. Enables investigation and reprocessing without blocking the main ETL load.

**Grain:** One row per individual column-level DQ violation per source row per ETL run.

**Load pattern:** `INSERT` by `migrate_staged_purchase_data.py` during QA-P003 RI checks and QA-P004 business rule assertions. Never updated; append-only.

**Delta properties:** `delta.autoOptimize.optimizeWrite = true`.

**Rules:** QA-P005, TY-017, NM-001, CX-P006

| # | Column Name | Data Type | Nullable | Description | Business Meaning | Derivation / Source |
|---|---|---|---|---|---|---|
| 1 | `rejection_id` | BIGINT | No | Surrogate primary key for the rejection record. Auto-generated by Delta's `GENERATED ALWAYS AS IDENTITY`. | Uniquely identifies a single DQ rejection event. Used as a stable reference key for downstream monitoring and reprocessing workflows. | `BIGINT GENERATED ALWAYS AS IDENTITY` — assigned by Delta on INSERT. Rule: TY-017. |
| 2 | `lineage_key` | BIGINT | No | Foreign key to `inventory_stock.bronze.lineage_run.lineage_key`. Links this rejection to the specific ETL run that detected it. | Enables correlation of all DQ rejections from a single pipeline run, and provides full traceability from a rejection back to the run's extraction window and success status. | Propagated via `dbutils.jobs.taskValues.get(taskKey="nb_extract_watermark", key="lineage_key")` and written to this column on INSERT. Rules: LN-001, LN-P001, QA-P005. |
| 3 | `rule_id` | STRING | No | The QA rule ID that detected this violation (e.g. `QA-P003`, `QA-P004`). | Classifies the type of quality issue, enabling monitoring dashboards to track violation counts by rule and prioritise remediation efforts. | Set by the calling Python code in `migrate_staged_purchase_data.py` at the point each QA check writes to the rejection table (e.g. `rule_id = "QA-P003"` for RI violations, `"QA-P004"` for business rule violations). |
| 4 | `source_table` | STRING | No | Fully qualified name of the source table from which the violating row was extracted (e.g. `inventory_stock.bronze.purchase_staging`). | Identifies where the bad data originated, narrowing down the investigation scope when rejections appear. | Set by the calling code to the table name from which the violating rows were read. |
| 5 | `pk_column` | STRING | No | Name of the primary key column used to identify the violating row in `source_table` (e.g. `purchase_staging_key`). | Enables direct lookup of the violating row in the source table for investigation. | Set by the calling code to the PK column name of the source table. |
| 6 | `pk_value` | STRING | No | String representation of the primary key value of the violating row. | Together with `pk_column` and `source_table`, uniquely identifies the violating row in the source table, enabling targeted reprocessing or manual correction. | Set by the calling code: `str(pk_value)` cast to STRING for uniform storage regardless of the PK data type. |
| 7 | `violation_column` | STRING | No | Name of the column whose value triggered the DQ rule violation (e.g. `supplier_key`, `ordered_quantity`). | Identifies exactly which field contains the problematic value, supporting targeted data quality monitoring and root-cause analysis. | Set by the calling code to the name of the column being validated (e.g. `"supplier_key"` for an RI check violation). |
