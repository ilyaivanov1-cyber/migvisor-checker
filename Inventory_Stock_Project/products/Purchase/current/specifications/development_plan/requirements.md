## 1. Functional Requirements

| ID | Title | Description | Priority | Acceptance Criterion | Source |
|---|---|---|---|---|---|
| FR-001 | Daily incremental extract from bronze staging | The product must consume incremental purchase order lines from `inventory_stock.bronze.purchase_staging` each nightly run. The staging table must be written in OVERWRITE mode before any transformation begins to ensure no stale rows carry forward from a prior run. | must-have | After each nightly run, `bronze.purchase_staging` contains only rows with `_extracted_at_utc` equal to the current run's extraction timestamp; no rows from a prior run are present. | x-inputPorts / purchase_staging |
| FR-002 | Watermark-bounded incremental extraction | The product must extract rows from the upstream source whose modification timestamp falls between the previous ETL cutoff (exclusive) and the current run cutoff (inclusive). The extract window boundaries must be read from `inventory_stock.bronze.etl_cutoff` at job start by `nb_extract_watermark`. | must-have | After each successful run, `bronze.etl_cutoff` is updated to the current run's cutoff timestamp; the next run extracts only rows modified after that timestamp. | x-inputPorts / etl_cutoff |
| FR-003 | Lineage key propagation via Workflow taskValues | The product must generate a unique lineage key per ETL run by inserting a record into `inventory_stock.bronze.lineage_run` (IDENTITY column), then publish the key via `dbutils.jobs.taskValues.set(key="lineage_key")` in `nb_extract_watermark`. All downstream tasks must consume the key via `dbutils.jobs.taskValues.get`. | must-have | Every row written to `silver_fact.fact_purchase`, `bronze.purchase_staging`, and `bronze.dq_rejections` in a given run carries the same `lineage_key` value; `bronze.lineage_run` contains exactly one record per run with matching `lineage_key`. | x-inputPorts / etl_cutoff + SLA |
| FR-004 | SCD-2 surrogate key resolution for supplier | The product must resolve `supplier_key` for each staging row by performing a temporal range join against `inventory_stock.silver_dim.supplier` using the row's modification timestamp and the dimension's `valid_from`/`valid_to` DATE columns (cast to TIMESTAMP for comparison). When multiple versions match, the most recent valid version (ORDER BY `valid_from DESC`) is selected. Unresolved rows receive `supplier_key = 0`. | must-have | After `sk_resolver.py` executes: (a) every staging row with a matching supplier dimension version carries a non-zero `supplier_key`; (b) staging rows with no matching version carry `supplier_key = 0`; (c) no staging row has a null `supplier_key`. | x-inputPorts / supplier_dimension |
| FR-005 | SCD-2 surrogate key resolution for stock item | The product must resolve `stock_item_key` for each staging row using the same temporal range join pattern as FR-004, joining against `inventory_stock.silver_dim.stock_item`. Unresolved rows receive `stock_item_key = 0`. | must-have | After `sk_resolver.py` executes: (a) every staging row with a matching stock item dimension version carries a non-zero `stock_item_key`; (b) staging rows with no matching version carry `stock_item_key = 0`; (c) no staging row has a null `stock_item_key`. | x-inputPorts / stock_item_dimension |
| FR-006 | Date key derivation | The product must derive `date_key` for each staging row from the order date column, expressed as a DATE value that matches the primary key of `inventory_stock.silver_dim.date` (the `date` column, DATE type). | must-have | After `nb_extract_purchase` executes: every staging row has a non-null `date_key`; the `date_key` value exists in `silver_dim.date.date` for every row that has a valid order date. | x-inputPorts / date_dimension |
| FR-007 | Fact table upsert via Spark SQL MERGE INTO | The product must load resolved staging rows into `inventory_stock.silver_fact.fact_purchase` using a Spark SQL `MERGE INTO` statement keyed on `wwi_purchase_order_id`. Matched rows must update all mutable columns; unmatched rows must be inserted. The MERGE must be idempotent for the same `wwi_purchase_order_id` and `lineage_key` combination. | must-have | Running the MERGE twice with the same staging input produces the same `silver_fact.fact_purchase` row count; `bronze.lineage_run.table_row_count` is populated with the actual merged row count after each run. | Details + dataAccess / fact_purchase_sql_warehouse |
| FR-008 | Conditional OPTIMIZE after fact merge | The product must execute `OPTIMIZE inventory_stock.silver_fact.fact_purchase` only when `rows_merged > FACT_OPTIMIZE_ROW_THRESHOLD` (10,000). The threshold must be read from `config/environment.yaml` under `purchase.etl.fact_optimize_row_threshold`. | should-have | When `rows_merged > 10000`, OPTIMIZE executes after the MERGE and log entry is written; when `rows_merged <= 10000`, OPTIMIZE is skipped and no OPTIMIZE log entry appears. | Details / x-inputPorts + CX-P001 |
| FR-009 | Configuration externalisation | All date filter boundaries and business validation parameters must be read from `config/environment.yaml` at notebook startup. No hard-coded date literals or business-factor constants may appear in ETL notebooks or SQL files. | must-have | Static scan of `src/etl/` finds zero hard-coded ISO date literals; `config/environment.yaml` contains all externalised values under `purchase.etl` and `purchase.business_rules`. | Details / CX-P001 + CX-P002 |
| FR-010 | Databricks SQL Warehouse data delivery | The product must expose `inventory_stock.silver_fact.fact_purchase` for BI consumption via a Databricks SQL Warehouse connected to Unity Catalog `inventory_stock`. The two Power BI reports must be connectable to the SQL Warehouse using their updated target-schema table and column references. | must-have | Both Power BI reports connect to the Databricks SQL Warehouse endpoint without error; `SELECT COUNT(*) FROM inventory_stock.silver_fact.fact_purchase` returns a non-zero row count after first successful load. | dataAccess / bi_reports |
| FR-011 | Environment initialisation notebook | The product must provide a `reseed_purchase_environment.py` notebook that (a) creates all required Bronze and Silver tables if they do not exist using `IF NOT EXISTS` DDL guards, (b) inserts `key=0` sentinel rows into `silver_dim.supplier` and `silver_dim.stock_item` if not already present, and (c) resets `bronze.etl_cutoff` to the configured `initial_load_date`. Execution requires explicit scope-owner sign-off (PD-002) and must be idempotent — running it twice must not duplicate sentinel rows or corrupt the watermark. | must-have | After `reseed_purchase_environment.py` executes: all required tables exist; `SELECT COUNT(*) FROM silver_dim.supplier WHERE supplier_key = 0` returns exactly 1; `SELECT etl_cutoff FROM bronze.etl_cutoff WHERE table_name = 'fact_purchase'` returns the configured initial load date; a second execution produces no errors and no additional sentinel rows. | Details / x-inputPorts + PD-002 |
| FR-012 | Mart layer population for BI consumption | The product must populate two mart-layer views in `inventory_stock.mart` after each successful fact merge: (a) `mart.v_purchase_by_supplier` — aggregate view joining `silver_fact.fact_purchase` to `silver_dim.supplier` for supplier-level order volume and fill-rate analysis; (b) `mart.v_purchase_per_stock_item` — aggregate view joining `silver_fact.fact_purchase` to `silver_dim.stock_item` for stock-item-level procurement analysis. Both views must be queryable by the `bi-service-principal` via Unity Catalog RBAC without additional grants beyond the standard role matrix. | must-have | After a successful nightly run, `SELECT COUNT(*) FROM mart.v_purchase_by_supplier` and `SELECT COUNT(*) FROM mart.v_purchase_per_stock_item` return non-zero values; both views are accessible to the `bi-service-principal` without error; the two Power BI reports can reconnect to these views via Databricks SQL Warehouse. | dataAccess / bi_reports + NFR-002 |

## 2. Non-Functional Requirements

| ID | Title | Description | Priority | Acceptance Criterion | Source |
|---|---|---|---|---|---|
| NFR-001 | Daily data freshness | Data in `silver_fact.fact_purchase` must reflect all upstream purchase records with modification timestamps up to midnight UTC of the preceding calendar day. The nightly ETL job must complete before 06:00 UTC. | must-have | `bronze.lineage_run.data_load_completed` for the most recent successful run is earlier than 06:00 UTC on the current calendar day; `silver_fact.fact_purchase` contains all rows with a modification timestamp ≤ midnight UTC of the prior day. | SLA / updateFrequency + latency |
| NFR-002 | SQL Warehouse availability | The Databricks SQL Warehouse endpoint must be available to BI consumers during business hours with ≥ 99.5% uptime. | should-have | Monthly uptime measurement of the SQL Warehouse endpoint is ≥ 99.5%; planned maintenance windows do not count against uptime. | SLA / uptime |
| NFR-003 | Row count reconciliation (blocking) | After each MERGE, the count of rows merged into `silver_fact.fact_purchase` must equal the count of rows in `bronze.purchase_staging` for the same batch. A mismatch must raise a `RuntimeError`, mark the Databricks Workflow task as FAILED, and prevent the lineage record from being closed as successful. | must-have | Injecting a mismatch between staging count and rows_merged causes the Workflow task to FAIL with `RuntimeError: Row count mismatch: staging=N, inserted=M`; `bronze.lineage_run.was_successful` is `false` for that run. | dataQuality / completeness |
| NFR-004 | Referential integrity validation (non-blocking) | Referential integrity of all three FK columns (`date_key`, `supplier_key`, `stock_item_key`) must be checked after each MERGE via LEFT ANTI JOIN. Violations must be written to `inventory_stock.bronze.dq_rejections` with `lineage_key`, `rule_id = 'QA-P003'`, and column-level detail. The pipeline must continue regardless of violation count. | must-have | After a load containing one invalid `supplier_key`: a rejection row is present in `bronze.dq_rejections` with `fk_column = 'supplier_key'`, `rule_id = 'QA-P003'`, and the matching `lineage_key`; the Workflow task status is SUCCEEDED. | dataQuality / consistency |
| NFR-005 | Orphaned surrogate key detection (non-blocking) | After each MERGE, the count of fact rows referencing a `supplier_key` or `stock_item_key` not present in any row of the respective dimension table (excluding key=0) must be computed and logged at WARNING level. The pipeline must not fail regardless of the count. | must-have | After loading one fact row with a non-zero `supplier_key` absent from `silver_dim.supplier`: a WARNING log entry `QA-P002: 1 orphaned supplier_key rows` is present; the Workflow task status is SUCCEEDED. | dataQuality / uniqueness |
| NFR-006 | Business rule assertions (non-blocking) | Three business rule assertions must run after each MERGE: (a) no negative `ordered_outers` or `ordered_quantity`; (b) `date_key` within the expected batch window; (c) no null or empty `package`. Violations must be logged at WARNING level; the pipeline must not fail. | must-have | Inserting one row with `ordered_outers = -1` produces WARNING `QA-P004: 1 rows with negative ordered_outers or ordered_quantity` in notebook logs; the Workflow task status is SUCCEEDED. | dataQuality / accuracy |
| NFR-007 | Centralised DQ rejection store | All DQ violation rows must be written to `inventory_stock.bronze.dq_rejections` using `spark.write.format("delta").mode("append")`. Every rejection row must include: `rejection_id` (IDENTITY), `lineage_key`, `rule_id`, `source_table`, `pk_column`, `pk_value`, `violation_column`, `violation_value`, `rejection_reason`, `detected_at`. | must-have | After environment initialisation, `DESCRIBE TABLE bronze.dq_rejections` returns all nine required columns with the correct data types. Rejection rows from QA-P003 are queryable by `lineage_key` after a run that produces RI violations. | dataQuality / traceability |
| NFR-008 | Unity Catalog access control | `silver_fact.fact_purchase` must be readable by BI service principals and data analysts via Unity Catalog RBAC. `bronze.*` tables must be accessible only to ETL service principals. `bronze.dq_rejections` must be readable by the data engineering team. Access role matrix definition is pending (PD-003). | must-have | A BI service principal can execute `SELECT COUNT(*) FROM silver_fact.fact_purchase` without error; the same principal receives `PERMISSION_DENIED` on `bronze.purchase_staging`. | governance / Unity Catalog + PD-003 |
| NFR-009 | Standard ETL notebook skeleton | Every Purchase ETL notebook in `src/etl/` and `src/init/` must follow the standard skeleton: (1) imports, (2) `lineage_key` from taskValues, (3) zero-rows guard, (4) main ETL logic with exception handler, (5) conditional OPTIMIZE, (6) close lineage. The `close_lineage_record` call must appear in both the success path and the `except` block. | must-have | Static analysis of every `.py` file in `src/etl/` confirms the six sections appear in order; a test that injects an exception in main ETL logic verifies `close_lineage_record(spark, lineage_key, rows_merged=0, succeeded=False)` is called. | Details / CX-P005 |
| NFR-010 | Standard DDL file header block | Every `.sql` file in `src/db/ddl/` must begin with the standard header block containing PROJECT, PRODUCT, FILE, PURPOSE, SOURCE, TARGET, RULES, and GENERATED fields. The RULES field must be non-empty and list every rule ID that influenced the file. | must-have | `grep -l '-- PROJECT  : Inventory_Stock_Project' src/db/ddl/*.sql` returns all `.sql` files in that directory; `grep -c '-- RULES    : $' src/db/ddl/*.sql` returns 0 (no empty RULES fields). | Details / CX-P006 |
| NFR-011 | Codebase layout conformance | All generated and hand-written artifacts must be placed under the standard Purchase codebase layout: `config/`, `docs/`, `src/common/`, `src/db/ddl/`, `src/etl/`, `src/init/`, `tests/`. No artifact may be placed outside this layout without a rationale comment. | must-have | After code generation, `os.path.isdir` returns `True` for all required top-level directories; the four required `src/common/` modules (`constants.py`, `scd2_merge.py`, `sk_resolver.py`, `fact_merge.py`) all exist. | Details / CX-P004 |
| NFR-012 | Data retention | `silver_fact.fact_purchase` and `silver_dim.*` tables must be retained for a minimum of 7 years. `bronze.*` tables must be retained for a minimum of 90 days. Retention policy must be enforced via Unity Catalog table retention configuration. | should-have | Unity Catalog table properties for `silver_fact.fact_purchase` include a data retention setting of ≥ 7 years; `bronze.purchase_staging` includes a retention setting of ≥ 90 days. | SLA / retentionPolicy |

## 3. Data Quality Requirements

| ID | Title | Description | Priority | Acceptance Criterion | Source |
|---|---|---|---|---|---|
| DQR-001 | Row count reconciliation — zero tolerance | The count of rows inserted into `silver_fact.fact_purchase` per batch must exactly equal the count of rows in `bronze.purchase_staging` for the same batch. | must-have | Post-MERGE assertion: `inserted_count == staging_count`; any deviation raises `RuntimeError` with the message `Row count mismatch: staging=<N>, inserted=<M>`. | dataQuality / completeness / QA-P001 |
| DQR-002 | RI completeness — supplier_key | Every non-zero `supplier_key` in `silver_fact.fact_purchase` for a given batch must have a matching row in `silver_dim.supplier`. Violations are written to `bronze.dq_rejections` with `rule_id = 'QA-P003'`. | must-have | LEFT ANTI JOIN on `supplier_key` returns zero rows for a clean load; rows that violate RI appear in `bronze.dq_rejections` within the same run. | dataQuality / consistency / QA-P003 |
| DQR-003 | RI completeness — stock_item_key | Every non-zero `stock_item_key` in `silver_fact.fact_purchase` for a given batch must have a matching row in `silver_dim.stock_item`. Violations are written to `bronze.dq_rejections` with `rule_id = 'QA-P003'`. | must-have | Same acceptance pattern as DQR-002 for `stock_item_key`. | dataQuality / consistency / QA-P003 |
| DQR-004 | RI completeness — date_key | Every `date_key` in `silver_fact.fact_purchase` for a given batch must have a matching row in `silver_dim.date`. Violations are written to `bronze.dq_rejections` with `rule_id = 'QA-P003'`. | must-have | LEFT ANTI JOIN on `date_key` against `silver_dim.date.date` returns zero rows for a clean load; violations appear in `bronze.dq_rejections`. | dataQuality / consistency / QA-P003 |
| DQR-005 | Quantity non-negativity | `ordered_outers` and `ordered_quantity` must be ≥ 0 for all rows loaded in a given batch. | should-have | Zero rows with negative values in a clean load; when violations are present, WARNING log entry `QA-P004: N rows with negative ordered_outers or ordered_quantity` is emitted and the pipeline completes without FAILED status. | dataQuality / accuracy / QA-P004 |
| DQR-006 | Date key within batch window | `date_key` must fall within the expected batch window (bounded by `batch_date_min` and `batch_date_max` derived from the extract watermark). | should-have | Zero rows with out-of-window `date_key` in a clean load; violations produce WARNING log entry and pipeline completes without FAILED status. | dataQuality / accuracy / QA-P004 |
| DQR-007 | Package non-null | `package` must be non-null and non-empty for all rows loaded in a given batch. | should-have | Zero rows with null or empty `package` in a clean load; violations produce WARNING log entry and pipeline completes without FAILED status. | dataQuality / accuracy / QA-P004 |
| DQR-008 | DQ rejection traceability | Every DQ violation row written to `bronze.dq_rejections` must carry the `lineage_key` of the ETL run that produced it, enabling surgical investigation and batch replay. | must-have | `SELECT DISTINCT lineage_key FROM bronze.dq_rejections WHERE lineage_key = <run_key>` returns exactly one distinct value equal to the run's `lineage_key`. | dataQuality / traceability / QA-P005 |
| DQR-009 | Surrogate key default coverage | Every staging row must have non-null values for `supplier_key` and `stock_item_key` after SK resolution. Rows that cannot be resolved to a dimension version receive `key = 0` (sentinel); they must not receive `NULL`. | must-have | After `sk_resolver.py` executes, `SELECT COUNT(*) FROM bronze.purchase_staging WHERE supplier_key IS NULL OR stock_item_key IS NULL` returns 0. | x-inputPorts / supplier_dimension + stock_item_dimension / FR-004 + FR-005 |
