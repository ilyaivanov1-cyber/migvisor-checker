## What This Spec Is

The product brief is the **engineering opinion** the migration team brings to the table before any rule is generated. It states, in advance and in one place, *how* this product should be migrated: what names look like, which types map to what, which T-SQL constructs disappear, how tables are laid out, what quality checks run, and what the generated codebase looks like on disk.

It is the only product-level document in this project that is an **input**, not an output. Every other spec — as-is, transformation rules, to-be, development plan — is generated by a migVisor skill. This one is written by a human and read by the skills.

It has 8 sections:

1. **Naming** — the identifier convention and its edge cases
2. **Column Type Rules** — source-to-target type mappings, plus the SCD-2 control block
3. **Calculation and Business Logic Rules** — derived columns, hard-coded values, duplicate functions
4. **Object Patterns** — target design per object class (SCD-2 dim, calendar, staging, views, UDFs)
5. **Syntax Transformations** — a 15-row T-SQL → Spark translation table
6. **Performance** — clustering strategy selection and OPTIMIZE policy
7. **Data Quality** — 4 assertions and their blocking behavior
8. **Output Structure** — the codebase tree plus SQL and Python file conventions

Think of it as the **standards document handed to the generator**. The scope says what to build; the brief says how to build it.

## Why This Spec Exists

### Without it, the generator invents conventions

Rule generation without a brief produces defensible but arbitrary output. `MONEY` could reasonably map to `DECIMAL(18,2)`, `DECIMAL(19,4)`, or `DOUBLE`. A `geography` column could become a WKT string, a struct, or two doubles. Notebooks could live in `src/etl/facts/` or `notebooks/fact/`. Each choice is fine in isolation; the problem is that nobody decided, so nothing is verifiable and the next product picks differently.

The brief front-loads those decisions and states the reason where the reason matters — "never use FLOAT for monetary values," "collation dropped; Spark defaults to UTF-8," "Delta snapshot isolation makes NOLOCK unnecessary." A generated rule can then cite the brief instead of inventing a justification.

### It is where the product rules come from

The relationship between this file and the generated product transformation rules is close to one-to-one. Nearly every one of the 26 Purchase customizations traces back to a paragraph here:

| Brief section | Dimension | Product rules it produced |
|---|---|---|
| Column Type Rules | TY | TY-P001 (SCD-2 validity → DATE), TY-P002 (5-column SCD-2 block), TY-P003 (MONEY/SMALLMONEY), TY-P004 (geography decomposition) |
| Object Patterns | OB | OB-P001 (key=0 sentinel bootstrap), OB-P002 (staging audit columns), OB-P003 (view materialization), OB-P004 (named shared helpers) |
| Syntax Transformations | SX | SX-P001 (taskValues lineage injection), SX-P002 (CONVERT style 112), SX-P003 (sk_resolver pre-join), SX-P004 (lineage close UPDATE) |
| Performance | PE | PE-P001 (fallback partition + Z-ORDER), PE-P002 (conditional OPTIMIZE threshold) |
| Data Quality | QA | QA-P001 through QA-P005 — the **entire QA dimension**, which has no project-level equivalent |
| Calculation and Business Logic | CX | CX-P001 (date externalization), CX-P002 (business factor externalization), CX-P003 (UDF consolidation) |
| Output Structure | CX | CX-P004 (codebase layout), CX-P005 (notebook skeleton), CX-P006 (DDL header block) |
| Naming | NM | Nothing — see below |

This is the most useful thing to know about the brief: it is not background reading. It is the **upstream cause** of the product rule set, and reading it explains why those 26 rules exist and no others.

### The Naming section produced nothing — and that is the point

Naming is the one section that generated zero product customizations. The project rules already cover snake_case conversion, space removal, and schema mapping (9 NM rules, fully inherited by Purchase with no changes). The brief's naming section **agrees** with them.

That agreement is worth noticing. A brief section that produces no rules is either redundant with the project level or is a boundary the product chose not to move. Either way, the absence of NM customizations tells you naming is settled project-wide — which is exactly what the product rules doc reports ("NM — Naming (9 rules), fully inherited").

## Section 1 — Naming

### What it contains

The convention (`lowercase_snake_case` throughout), four illustrative transformations, and four specific conventions.

| Example | Shows |
|---|---|
| `SalespersonKey` → `salesperson_key` | PascalCase → snake_case |
| `WWIInvoiceID` → `wwi_invoice_id` | Acronyms lowercased with underscores inserted |
| `Dimension.Stock Item` → `dim.stock_item` | Space → underscore **and** schema remapped |
| `getTotalQuantitySold1` → `get_total_quantity_sold` | camelCase procedure → Python function, numeric suffix dropped |

Plus: bracket quoting (`[Column Name]`) removed and renamed at DDL generation time; no backtick-quoted identifiers; views take a `v_` prefix; staging tables take a `_staging` suffix — with `etl_cutoff` called out as an exception because control tables are not staging tables.

### Why this section matters

Two details do real work.

**The `[Column Name]` rule fixes the timing, not just the outcome.** Renaming happens *at DDL generation time*, which means the target table is created with the snake_case name and nothing downstream ever sees the bracketed form. The alternative — creating tables with the legacy names and aliasing at query time — would push the legacy naming into every view and report. `fact.purchase` has `Date Key`, `Supplier Key`, `Stock Item Key`, `WWI Purchase Order ID`, `Ordered Outers`, `Is Order Finalized`, `Lineage Key` — seven bracketed columns on one table, so this is not a marginal case.

**The `etl_cutoff` exception prevents a mechanical mistake.** A generator applying "`_staging` suffix on staging tables" without the carve-out would produce `etl_cutoff_staging`, which is wrong: the cutoff table is durable control state, not transient staging. Naming it as staging would also imply the truncate-and-reload policy from §4 applies to it, which would destroy the watermark on every run. The exception is a one-line note guarding against a data-loss bug.

## Section 2 — Column Type Rules

### What it contains

A 9-row mapping table listing **only non-trivial mappings**, followed by the 5-column SCD-2 control block.

| Source | Target | The reason given |
|---|---|---|
| NVARCHAR(n) / VARCHAR(n) / NVARCHAR(MAX) | STRING | Collation dropped; Spark defaults to UTF-8 |
| DATETIME / DATETIME2 / SMALLDATETIME | TIMESTAMP | Operational timestamps only — SCD-2 validity is the exception |
| BIT | BOOLEAN | e.g. `Is Order Finalized` |
| MONEY / SMALLMONEY | DECIMAL(18,2) / DECIMAL(10,2) | **Never use FLOAT for monetary values** |
| DECIMAL(p,s) / NUMERIC(p,s) | DECIMAL(p,s) | Preserve precision and scale exactly |
| VARBINARY | BINARY | e.g. `Photo` columns |
| BIGINT IDENTITY (fact PK) | BIGINT GENERATED ALWAYS AS IDENTITY | Sequence objects retired |
| INT IDENTITY (dim PK) | INT GENERATED ALWAYS AS IDENTITY | Dimension surrogate keys |
| geography | 3 columns: `location_wkt STRING`, `location_lat DOUBLE`, `location_lon DOUBLE` | CLR spatial type has no Spark equivalent; extract via `STAsText()`, `.Lat`, `.Long` **at source** |

The SCD-2 control block: `valid_from DATE NOT NULL`, `valid_to DATE NOT NULL` (business dates), `row_effective_date DATE NOT NULL`, `row_expiry_date DATE NOT NULL DEFAULT DATE '9999-12-31'`, `is_current_row BOOLEAN NOT NULL DEFAULT TRUE`.

### Details worth noting

**"Only types that require a non-trivial mapping are listed."** The opening sentence is a scoping instruction to the reader and to the generator: `INT → INT` and `DATE → DATE` are identity mappings and are deliberately absent. Their absence is not an oversight to be filled in.

**The DATETIME row contains its own exception.** It maps to TIMESTAMP but flags that SCD-2 validity columns use DATE instead. This one line is the origin of **TY-P001**, the single override in the entire Purchase product rule set — it contradicts project rule TY-012 (`DATETIME2 → TIMESTAMP_NTZ`) for exactly two columns. The brief states the divergence at the point where a reader would otherwise apply the general rule.

**The SCD-2 block distinguishes business dates from technical dates.** `valid_from`/`valid_to` are labelled *business* effective/expiry; `row_effective_date`/`row_expiry_date` are labelled *technical* row open/close. These are four DATE columns that look interchangeable and are not: business dates come from the source data, technical dates come from the load process. Conflating them breaks point-in-time queries in ways that are hard to detect, because both pairs produce plausible-looking results.

**`geography` extraction happens at source.** The brief specifies `STAsText()`, `.Lat`, `.Long` — SQL Server CLR methods. Spark cannot decompose a geography value it never received, so the extraction has to be in the source-side SELECT. Naming the methods makes the extract query writable without a research detour. `dimension.supplier` has a `DeliveryLocation` column, so this fires for Purchase's read dependency.

### Why this section matters

Type mappings are the highest-volume, lowest-visibility source of migration defects. A wrong `MONEY → DOUBLE` mapping produces rounding drift that appears months later in a financial reconciliation, with no error and no log entry. The "never use FLOAT" instruction exists because that mapping is a common and silent mistake.

## Section 3 — Calculation and Business Logic Rules

### What it contains

Four subsections, each written **conditionally** — "If the source procedure computes…", "Analytics views **may** contain…", "If a view applies…", "If the source contains…".

| Subsection | The rule | The mechanism |
|---|---|---|
| Derived financial columns | Preserve stored-column derivation; **do not re-derive at query time** | Compute in the ETL notebook (`withColumn` chain shown in Python) |
| Hard-coded date filters | Replace literals and rolling windows with named parameters | `config/environment.yaml` under `date_filters:` — plus a stakeholder confirmation item when the business meaning is unclear |
| Hard-coded business factors | Externalise unexplained multipliers as named constants | `environment.yaml` + NULL guard (`CASE WHEN denominator = 0 THEN NULL`) + DQ bound assertion + stakeholder confirmation before go-live |
| Duplicate functions | Consolidate functionally identical scalar functions into one UDF | Add `COALESCE(SUM(...), 0)` guard if absent; register both source names as `CONSOLIDATED → <target_name>` in the object registry |

### Why the conditional phrasing is deliberate

Most of this section does not fire for Purchase, and the brief is written so that non-firing is silent rather than wrong.

Purchase's scope (§6 Calculation Surface) records that the product owns **no scalar UDFs and no analytics views**, and the fact table's measures are `Ordered Outers`, `Ordered Quantity`, `Received Outers`, `Package` — no financial aggregates. So:

- **Derived financial columns** — the `total_excluding_tax` / `tax_amount` / `total_including_tax` example is drawn from the Sales domain. Purchase has no such columns; the rule is dormant.
- **Duplicate functions** — the `getTotalQuantitySold1` / `getTotalQuantitySold2` pair is illustrative. Purchase has no scalar functions to consolidate, yet **CX-P003** still exists in the product rules as a standing consolidation policy.

This is what makes the brief reusable: it is written once for the project and applied per product, with conditionals so that inapplicable guidance produces no rules instead of producing rules against objects that do not exist.

The two subsections that **did** fire — date filters and business factors — became **CX-P001** and **CX-P002**. Note what CX-P002 kept and what it changed: it kept the externalization and the guards, and it hardened the NULL guard from the brief's `CASE WHEN denominator = 0` into `if val is None: raise ValueError` plus a bound assertion. The brief guarded against division by zero; the product rule also guards against a missing config key, which is the failure the externalization itself introduces.

### The stakeholder confirmation pattern

Both the date-filter and business-factor subsections end the same way: add a stakeholder confirmation item. The brief's own YAML example carries the comment `# preserves source literal; confirm with stakeholders`.

This is the same discipline as the `[USER INPUT REQUIRED]` placeholders in the product scope. Externalizing `WHERE order_date > '20230101'` into a config key preserves the behavior exactly but does not explain it — nobody knows whether that date is a business epoch, a data-availability floor, or a leftover from testing. Externalization makes the value changeable; the confirmation item makes the question visible. Doing only the first produces a config file full of unexplained magic numbers.

## Section 4 — Object Patterns

### What it contains

Target design specifications for 5 object classes.

**SCD-2 dimension tables** — surrogate key becomes `INT GENERATED ALWAYS AS IDENTITY` (sequence retired); the 5 control columns; **two-step Delta MERGE** loading (Step 1 expires the current row: `is_current_row = FALSE`, `row_expiry_date = effective_date - 1`; Step 2 inserts the new active version); logic centralized in shared `scd2_merge.py`; and a key=0 "Unknown" sentinel row required in every dimension **before any fact load**, created by a one-time bootstrap notebook.

**Static calendar table** — no SCD-2 columns, no `lineage_key`. Primary key is `date_key INT` in **YYYYMMDD integer format, not a DATE column**. Pre-loaded reference table; the source's day-loop procedure is replaced by `nb_populate_dim_date.py` that inserts the full year range once. **No daily reload.**

**Staging tables** — transient Delta, truncate-and-reload every run, plus two mandatory audit columns: `lineage_key BIGINT NOT NULL` (FK to `stg.lineage`, identifies the run) and `_extracted_at_utc TIMESTAMP NOT NULL`. No OPTIMIZE, no partitioning, short Delta log retention.

**Analytics views** — aggregating/reporting views become `CREATE OR REPLACE MATERIALIZED VIEW`; thin wrapper/alias views become `CREATE OR REPLACE VIEW`. Remove `WITH (NOLOCK)` — Delta snapshot isolation makes it unnecessary. Views referencing out-of-scope tables are stubbed with a TODO and the dependency documented.

**Scalar UDFs** — Databricks SQL UDFs in Unity Catalog or Python functions in a shared module; always add NULL guards if the source lacks them.

### Details worth noting

**The two-step MERGE is specified as two steps, in order.** SCD-2 is where migrations most often produce subtly wrong history. Expiring the old row and inserting the new one in the wrong order, or in a single statement, yields overlapping validity windows — two rows claiming to be current for the same business key. Point-in-time joins then return duplicates. `row_expiry_date = effective_date - 1` is the detail that makes the windows adjacent instead of overlapping.

**The sentinel row is a load-order requirement, not a data-seeding note.** "Must be present in every SCD-2 dimension **before any fact load**" is a sequencing constraint. The fact load resolves unmatched keys to 0 via `COALESCE(resolved_key, 0)` (§5), so if row 0 does not exist, the fact table accumulates FK values pointing at nothing. The brief pairs the requirement with its mechanism — a one-time bootstrap notebook, separate from the nightly pipeline. This became **OB-P001**, which added idempotency (MERGE not INSERT) and a post-execution assertion.

**`date_key INT` in YYYYMMDD is emphasized because the intuitive choice is wrong.** A date key that stores a date "should" be a DATE column. But `fact.purchase.Date Key` joins to it, and every downstream query and report expects the integer form. Changing it to DATE would silently break every join that passes an integer. The brief says "not a DATE column" explicitly because a generator optimizing for type correctness would get this wrong.

**"No daily reload" is a cost and correctness instruction.** The source populates the calendar via a day-loop procedure. Porting that loop faithfully gives a nightly job that rewrites a static table for no reason. The replacement runs once.

**Analytics views and UDFs mostly do not apply to Purchase** — the scope records no owned views or UDFs. But the materialization split still became **OB-P003**, because the *to-be design* introduces target views: `_current` views over SCD-2 dimensions (thin filters on `is_current_row = TRUE`, kept as regular views) and gold analytics views (aggregating, materialized). The brief's guidance carried forward to views that did not exist in the legacy system.

### Why this section matters

Sections 2 and 5 handle mechanical translation — one type or construct at a time. This section handles **design**: the shape of the target object, which cannot be derived from the source object alone. `Valid From`/`Valid To` in SQL Server does not tell you that the target needs five control columns, a two-step merge, and a sentinel row. That is a design decision, and this is where it is recorded.

## Section 5 — Syntax Transformations

### What it contains

A 15-row T-SQL → target table. It splits into three groups.

**Constructs that simply disappear (4):**

| Source | Why it goes |
|---|---|
| `SET NOCOUNT ON`, `SET XACT_ABORT ON` | No Databricks equivalent |
| `BEGIN TRAN` / `COMMIT` / `ROLLBACK` | Delta MERGE is per-statement atomic; multi-table logic uses sequential idempotent writes with checkpoint |
| `WITH EXECUTE AS OWNER` | Replaced by the Databricks service principal |
| `NEXT VALUE FOR [Sequences].[...]` | The IDENTITY column generates the key |
| `WITH (NOLOCK)` | Delta snapshot isolation; flag any out-of-scope tables referenced |

**Direct function substitutions (4):** `GETDATE()`/`SYSDATETIME()` → `current_timestamp()`; `ISNULL(x,y)` → `ifnull`/`coalesce`; `TOP(1)` in a correlated subquery → `LIMIT 1 with ORDER BY valid_from DESC`; `[Bracket Quoted Identifier]` → snake_case, unquoted.

**Structural rewrites (6)** — where the shape of the logic changes, not just its spelling:

| Source pattern | Target |
|---|---|
| `UPDATE staging SET key = (SELECT TOP(1) key FROM dim WHERE biz_key = … AND valid_from <= … AND valid_to > …)` | **Pre-join step before MERGE** — `JOIN dim ON biz_key AND date BETWEEN valid_from AND valid_to`, handled by `sk_resolver.py` |
| `DELETE fact WHERE biz_key IN (SELECT … FROM staging)` | `MERGE INTO fact … WHEN MATCHED THEN DELETE`, or a full MERGE |
| `COALESCE(subquery, 0)` — Unknown member fallback | **Preserve** as `COALESCE(resolved_key, 0)` |
| `CONVERT(CHAR(8), GETDATE()-N, 112)` | `DATE_FORMAT(DATE_SUB(current_date(), N), 'yyyyMMdd')` |
| `EXEC Integration.GetLineageKey` | `dbutils.jobs.taskValues.get(taskKey="nb_extract_watermark", key="lineage_key")` |
| `UPDATE Integration.Lineage SET [Data Load Completed] = …` | `spark.sql(f"UPDATE {TBL_LINEAGE} SET rows_loaded = {rows_merged} WHERE lineage_key = {lineage_key}")` — inline after merge |

### Details worth noting

**The `TOP(1)` row appears twice, at two levels of abstraction.** Row 5 gives the local substitution (`LIMIT 1 with ORDER BY valid_from DESC`). Row 6 says the whole `UPDATE staging SET key = (subquery)` statement should not survive as an UPDATE at all — it becomes a join producing a resolved DataFrame, in `sk_resolver.py`. A translator working row-by-row would produce a correct-looking Spark UPDATE and miss the restructuring. Both rows are present because the mechanical answer and the design answer are different, and this is the single most important piece of logic in `migratestagedpurchasedata`.

**One row says "preserve."** `COALESCE(subquery, 0)` stays as `COALESCE(resolved_key, 0)`. Amid fifteen changes, marking the thing that must *not* change is as important as the changes — the key=0 fallback is load-bearing behavior tied to the sentinel row in §4, not incidental legacy defensiveness.

**`EXEC GetLineageKey` becomes an inter-task channel, not a function call.** The legacy procedure could be called from anywhere. The replacement is `taskValues.get` with a specific `taskKey` and `key`, meaning exactly one task (`nb_extract_watermark`) creates the lineage key and every other task receives it. The brief names both strings so generated notebooks reference them identically. This produced **SX-P001** and **LN-P001**.

**The transaction removal carries its own compensating control.** `BEGIN TRAN` is not simply deleted — the row states what replaces the guarantee: per-statement atomicity plus "sequential idempotent writes with checkpoint." Removing transactions without that note would leave multi-table logic with no consistency story at all.

### Why this section matters

This table is the working reference a developer or generator consults line by line while converting `migratestagedpurchasedata`. Purchase's scope calls the product "ETL-logic-heavy," and this table is why: all of that logic lives in one procedure, and nearly every row here fires against it.

## Section 6 — Performance

### What it contains

Clustering strategy selected from the **source indexing pattern**, plus OPTIMIZE policy per table class.

| Source has | Target strategy | Rationale |
|---|---|---|
| Clustered Columnstore Index (CCI) | `CLUSTER BY (date_col, fk_col_1, fk_col_2)` — liquid clustering | CCI is evidence of multi-dimensional columnar access; liquid clustering is the idiomatic replacement |
| Row-store B-tree on a date column | `PARTITIONED BY (date_col)` + `ZORDER BY (fk_col_1, fk_col_2)` | Date-range partition elimination plus Z-ORDER for secondary keys |

Dimension tables get no explicit `CLUSTER BY` — small enough that Delta's default layout suffices. OPTIMIZE runs on fact tables **conditionally in-notebook after merge**, only when `rows_merged > FACT_OPTIMIZE_ROW_THRESHOLD`. Mart views have a dedicated `nb_optimize_mart.py` task. Staging tables get no optimization.

### Why this section matters

**The strategy is inferred from evidence, not chosen by preference.** The source's index type is treated as a recorded statement about how the data is actually queried. A CCI means multi-dimensional columnar scans; a date B-tree means range scans. Reading the layout decision off the source index is more reliable than guessing an access pattern from the schema — which matters here, because Purchase's scope records `fact.purchase` as **rowstore**, selecting the partition + Z-ORDER branch. That became **PE-P001**, which the product rules also tie to a runtime constraint: liquid clustering needs DBR 13.3+, so partition + Z-ORDER doubles as the fallback, and the two strategies are mutually exclusive.

**Conditional OPTIMIZE is a cost control with a real trigger.** Purchase's nightly volume varies — some nights only a handful of orders change. Unconditional OPTIMIZE compacts a 5-row batch at full cluster cost. The threshold makes the compaction proportional to the work done.

### A divergence worth knowing about

The brief puts `FACT_OPTIMIZE_ROW_THRESHOLD` in `constants.py`. The generated product rule **PE-P002** externalizes it to `config/environment.yaml` instead (as `fact_optimize_row_threshold`), alongside the other externalized values from §3.

The product rule is the stricter reading of the brief's own logic: §3 says tunable values belong in `environment.yaml` so they can change without a code deployment, and a threshold in `constants.py` is code. Where the brief and the generated rules disagree, **the generated rules govern** — they are the spec the code generators read. This one is a resolved inconsistency in the brief, not an open question, but it is the kind of thing to check when brief and rules appear to say different things.

## Section 7 — Data Quality

### What it contains

Four assertions that run **after dimension/fact load, before mart promotion**, with failures written to `stg.dq_rejections`.

| # | Assertion | Blocking? |
|---|---|---|
| 1 | **Row count reconciliation** — staging count must equal the net delta in the fact table for the batch | **Zero tolerance**; pipeline alert on mismatch |
| 2 | **Dimension key integrity** — orphaned FK keys (key=0 or NULL where unexpected) flagged | No — review only |
| 3 | **Referential integrity** — all non-null FK columns must resolve in their dimension, via LEFT ANTI JOIN per FK column | No |
| 4 | **Business rule assertions** — product-specific (example given: `quantity >= received_outers`) | No — informational |

Traceability: DQ outcomes link through `lineage_key`. The `stg.lineage` row is updated with row counts by the fact load notebook, and rejections in `stg.dq_rejections` reference the same `lineage_key`.

### Why this section matters

**This section created an entire dimension.** The legacy system had no structured data quality checks at all — problems stayed invisible until a business user noticed wrong numbers in a report. There is no QA dimension in the project rules either. All 5 product QA rules (**QA-P001** through **QA-P005**) originate here, which makes this the highest-leverage section in the brief: it is the only place the migration adds a capability the source never had.

**One blocking check, three informational.** The classification is deliberate and the reasoning generalizes. Row count reconciliation blocks because a mismatch means rows were silently lost — the pipeline cannot be allowed to advance the watermark and close the lineage record as successful on top of that. The other three surface data problems that usually originate **upstream**, outside Purchase's control. Blocking on them would fail the pipeline nightly for defects the Purchase ETL cannot fix; logging them creates visibility without creating false outages.

**`lineage_key` is what makes the checks operationally useful.** Assertions that write to a log produce findings nobody can query. Rejections keyed to the run ID produce a filterable history: every violation joins back to the exact pipeline execution that produced it. **QA-P005** turned this into a concrete 10-column `dq_rejections` DDL.

**The example assertion was replaced with real ones.** The brief offers `quantity >= received_outers` as an illustration. The generated **QA-P004** specifies Purchase's actual invariants instead: `ordered_outers >= 0` and `ordered_quantity >= 0`, `date_key` within the expected batch window, and `package` not null or empty. The brief supplies the pattern and the blocking policy; the product rules supply the domain content.

## Section 8 — Output Structure

### What it contains

The most prescriptive section: a full codebase tree, plus a required SQL header block and a required Python notebook skeleton.

**The tree** — `config/` (13 files: cluster config, workflow definition, UC setup and permission audit, DQ assertion YAML, secrets config/setup/rotation runbook, deploy script, CI/CD pipeline, monitoring, pytest.ini, BI connections), `docs/` (architecture diagram, data dictionary, pipeline runbook, go-live checklist), and `src/` split into `common/` (`constants.py`, `utils.py`), `db/` (`ddl/`, `grants/`, `queries/`), and `etl/` with six task-group subfolders: `ingestion/`, `dimensions/`, `facts/`, `mart/`, `dq/`, `security/`.

**The stated reason for the layout:** "Folders map directly to Databricks Workflow task groups." The directory structure and the runtime task graph are the same structure.

**The SQL header block** — a boxed comment with filename, catalog, schema, table, and a purpose line that must note key design decisions (clustering, CDF, retention). Then the `CREATE TABLE IF NOT EXISTS` with commented column groups (surrogate key, dimension FKs, lineage, measures), `USING DELTA`, `CLUSTER BY`, and TBLPROPERTIES enabling Change Data Feed with 2555-day (7-year) file and log retention. Constraint naming: `pk_<schema>_<table>`, `uq_<table>_<col>`. **FK constraints are not emitted** — documented as lineage instead.

**The Python notebook skeleton** — a full worked example with `sys.path` insertion, imports from `constants.py` and helper modules, `lineage_key` retrieved from `taskValues` inside a try/except that raises `RuntimeError` on absence, a zero-rows guard that skips the merge cleanly, enrichment, `resolve_surrogate_keys`, `apply_fact_merge`, conditional OPTIMIZE, and the inline lineage UPDATE.

### Details worth noting

**Folders equal task groups.** This turns the layout from a style preference into a functional contract. `src/etl/facts/` is not just where fact code lives — it corresponds to a Workflow task group. Moving a notebook between folders implies moving a task in the runtime graph.

**Three named helper modules appear in the tree as first-class files:** `scd2_merge.py` (under `dimensions/`), `sk_resolver.py` and `fact_merge.py` (under `facts/`). This is what **OB-P004** promoted to explicit migration targets with defined interfaces and unit tests. Their placement encodes which layer owns them.

**FK constraints are deliberately not emitted.** Databricks does not enforce them, so emitting them would create documentation that reads like a guarantee and is not one. The brief routes that information to lineage documentation and to the RI assertion in §7 — which *does* enforce it, at load time, with results in `dq_rejections`. The relationship is documented in one place and enforced in another, and neither pretends to be the other.

**7-year retention is set at the table level.** `delta.deletedFileRetentionDuration` and `delta.logRetentionDuration` both at `interval 2555 days`, with Change Data Feed enabled. Retention is a compliance-shaped decision, and putting it in the template means every generated table gets it rather than depending on whoever writes the DDL remembering.

**The notebook skeleton is executable, not schematic.** It includes the specific failure behavior — `raise RuntimeError("lineage_key not available from nb_extract_watermark task values")` — and the zero-rows guard that logs and skips rather than merging an empty batch. The closing note draws the dim/fact distinction explicitly: `sk_resolver` and `fact_merge` are fact-notebook patterns; dimension notebooks call `apply_scd2_merge` directly.

### Why this section matters

This section is the interface between the specs and every downstream tool. Code generators write to these paths; the CI pipeline looks for artifacts at these paths; the documentation generator walks these folders; import statements assume this hierarchy. Without it, generated files land in plausible-but-different locations and nothing composes.

A single markdown file, ~340 lines, in `input/` rather than `current/specifications/` — because it is **authored, not generated**. It is the human contribution to the product's rule set, and it is read by the rule-generation skills rather than produced by them.

Two things to know when reading it:
